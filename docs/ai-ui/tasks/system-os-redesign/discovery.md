## Current architecture evidence

- App entry/routing: `frontend/src/app/app.routes.ts`, `app.config.ts`; core shell `features/shell/shell.layout.{ts,html,scss}`. There are 76 route lazy-load references and 69 distinct import paths, with shared components for alternate routes (vacancy form, hiring list/wizard, candidates, docs, profile, etc.).
- Route security: `authGuard` wraps the signed-in shell; child module guard wraps signed-in pages; role guard is per privileged route. `guestGuard` protects `/login`. `/jobs` and `/jobs/:slug` are public and outside shell. UI launcher state must be derived from permitted navigation and cannot substitute for router/API authorization.
- Existing appearance axis: `core/theme/theme.service.ts` preserves legacy `sinhrm.theme`, stores typed preferences locally, and applies `data-theme`, `data-color-scheme`, `data-accent`, `data-interface-style`, `data-wallpaper`, `data-performance`, `data-motion` plus `--os-glass-opacity` at the root. `app.config.ts` calls `ThemeService.init()` before awaiting auth load. `styles.scss` owns Material tokens, app aliases, color-scheme, system typography and common global components.
- Shell owns route-active nav, user role/profile menus, role switching, language switch, badges, drawer, collapse/auto-hide and current dark/light control. These behaviors are described in `shell.layout.ts`, `nav-rail.ts`, `nav-groups.ts`, and `shell.layout.html`.
- Shared UI includes Material config/dialog defaults (`core/ui/dialog.ts`; maxWidth 95vw and focus behavior), notifications, table sort/filter/request/URL state, translated paginator, icons/logo and feature dialogs. CDK overlays render outside feature component subtrees; global attributes/tokens must cascade to the overlay container.
- Feature screens navigate using absolute `routerLink` targets, query params and `Router.navigate`; many table filters/page/sort values are URL-backed. Root/SOL preflight additionally flags named-outlet dependencies and global URL/state assumptions for the later true-window phase. Treat that as a blocking architecture check before any route/window conversion; never create decorative pseudo-forms or a second fake page model.
- Current styles follow `docs/architecture/design-direction.md` (“Route”); a measured feature scan excluding tests saw 11 lines containing literal CSS colors in 8 of 284 style-bearing files, clustered in login artwork, org chart, shell and time-off settings. Global `styles.scss` is already the central source of canonical colors and aliases. A final implementation scan should distinguish styling literals from SVG/data-visualization values and assets.

## Recommended foundation seam

1. Keep effective light/dark independent from OS material and performance settings. Preserve `ThemeService.theme()` consumers and the legacy `sinhrm.theme` migration. The agreed preference API is typed and bounded; one authority applies validated root attributes/tokens, storage failure/corrupt values fall back safely, and the appearance form uses existing Material controls.
2. Put semantic OS tokens and their mapping in `frontend/src/styles.scss`: map them to the existing `--app-*` and Material variables, not into each routed feature by broad global CSS selectors. This can change the page canvas, cards, controls, tables, dialogs, menus, snackbar, status/focus colors and type system across token consumers.
3. Keep round-one preference work separate from future authenticated shell/window changes. When true windows are designed, keep them inside authenticated shell, use real route components, retain URL/router state as canonical for deep links/back/refresh and guards, and resolve named-outlet/query/global URL dependencies first. Verify vacancy CanDeactivate before close/switch; preserve drafts and component state. Workflows and script editors have their own dirty/save/publish contracts and need page-specific lifecycle review.
4. Token migration exceptions are small but real: handle branded login SVG, org-chart colors and shell/time-off literal style intentionally. Preserve semantic status distinctions; do not use opacity to weaken text, chart/data marks, or controls.
5. Scope glass to a few bounded, non-nested shell surfaces. Keep readable page contents, tables, charts and form controls opaque enough for contrast. At fast-mode or unsupported blur, render opaque CSS surfaces. Respect `prefers-reduced-motion`; avoid continuous/pointer animations and page-wide blur.
6. Avoid loading all route components in a giant desktop model or duplicating feature templates. Use existing lazy router/components and shared shell/navigation abstractions. Gate launcher entries with the same role/module-aware nav source where practical, while retaining actual route guards.
