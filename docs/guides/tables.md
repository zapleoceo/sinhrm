# Таблицы: сортировка и фильтры в заголовках

## Простыми словами
Во всех списках сайта заголовок колонки работает одинаково: **клик по названию** сортирует (стрелка ↑), **второй клик** —
в обратном порядке (↓); **воронка рядом** с названием открывает фильтр этой колонки (текст, выбор из списка или
диапазон «від–до»). Точка на воронке — фильтр включён, в окне фильтра есть «Очистити». Сортировка и фильтры
записываются в адрес страницы: ссылкой можно поделиться, кнопка «назад» возвращает предыдущий вид.

Первым так сделан список сотрудников `/people`. Остальные таблицы переводятся по списку ниже, по одной задаче на таблицу
или группу — **тем же компонентом**, второй способ не заводим.

## Как подключить заголовок
Компонент — `frontend/src/app/core/ui/table` (описание — [core.md](../modules/core.md#заголовок-таблицы-сортировка-и-фильтр)),
образец — `features/people/directory/people.page.ts` + `people.query.ts`.

1. **Решить, где сортировать и фильтровать** (колонка «Пагинация» в инвентаре):
   - **серверная** пагинация → сортирует и фильтрует API: в FormRequest `sort` — `Rule::enum(<Колонки>Sort)`, `dir` —
     `Rule::in(['asc','desc'])`, текстовые фильтры `nullable|string|max:100`; недопустимое значение → **422** (правило
     проекта, как у остальных фильтров). В репозитории — `match` по enum в свой `ORDER BY` (никакого текста запроса в SQL),
     связанные имена — подзапросом, `nulls last`, добивка по имени и `id`; `like` — только биндингом с экранированием
     `% _ \`. Скоупы доступа (филиалы, уволенные, роли) не трогаем — сортировка их не расширяет. Feature-тест: asc, desc,
     фильтр, недопустимая колонка → 422, `perPage` строкой. Образец — `People/Http/Requests/ListPeopleRequest.php`,
     `People/Repositories/EloquentEmployeeRepository.php`, `tests/Feature/People/PeopleSortFilterApiTest.php`.
   - **без пагинации** (все строки уже пришли) → сортировать и фильтровать на фронте: `computed` от строк, `sort` и
     фильтров (сравнение строк — `localeCompare` с языком интерфейса, пустые — в конце).
     Готовое — `core/ui/table/client-table.ts`: описать колонки `ClientColumns<T>` (`sort`, `filter`, `match`), на странице
     `table = new ClientTable(COLUMNS, defaultSort, onQuery)` и `rows = table.rows(items)`; фильтр без `match` — серверный
     (страница отправляет его в API в `onQuery`: так сделаны статус активов и обращений, потому что API отдаёт не больше
     300–500 строк). Образец — `features/assets/assets.page.ts`, `features/desk/queue.page.ts`, юнит —
     `assets.page.spec.ts` на хелпере `src/testing/table.ts`.
2. **Состояние в адресе:** `providers: [TableUrlState]`, функция «адрес → запрос» (как `peopleQueryFromParams`: мусор из
   адреса отбрасывается, а не уходит в API), в `ngOnInit` — `url.watch(parse, q => store.apply(q))`; изменения — только
   через `url.update({...})` (страница сама вернётся на 1; листание — `{ paging: true }`). Store не грузит повторно тот же
   запрос (`sameQuery`).
3. **Разметка:**
   ```html
   <table class="app-table" [appTableSort]="sort()" (appTableSortChange)="url.update(sortToParams($event))">
     <thead><tr>
       <th scope="col" app-column-header key="name" [label]="'x.fields.name' | transloco"
           [filter]="{ type: 'text' }" [filterValue]="query.name ?? null" (filterChange)="setFilter('name', $event)"></th>
       <th scope="col" app-column-header key="status" [label]="…" [filter]="statusFilter()" …></th>  <!-- type: 'select' -->
       <th scope="col" app-column-header key="created" [label]="…" [filter]="{ type: 'range', input: 'date' }" …></th>
       <th scope="col" app-column-header key="contact" [sortable]="false" [label]="…"></th>
     </tr></thead>
   ```
   `sort()` — из адреса, а если его нет — порядок API по умолчанию (чтобы стрелка стояла на нужной колонке).
   Для `mat-table` — тот же атрибут на `<th mat-header-cell app-column-header …>`.
4. **Ничего не потерять:** верхний фильтр, привязанный к колонке, переезжает в её заголовок; не привязанный (поиск,
   статус без своей колонки, переключатель вида) — остаётся сверху. Если колонка скрыта на узком экране или есть вид
   «карточки», её фильтр остаётся и сверху для этих случаев (см. `.dict` в `people.page.ts`).
5. **Проверка:** юнит страницы (адрес → запрос, клик → `sort/dir` в адресе и страница 1), e2e-флоу в
   `frontend/e2e/flows.pw.ts`, эталоны инвентаря (`npm run e2e:update`) — **только затронутой страницы**, разница
   осознанная (новые кнопки заголовков, переехавшие поля); `axe-baseline.json` и `layout-allowlist.json` не ослаблять.
   Рендер 1440 и 390, светлая и тёмная тема: страница без горизонтальной прокрутки, таблица прокручивается в своей панели.

## Инвентарь таблиц сайта
Снят 2026-10-02 (`grep` по `mat-table`, `<table`, `.app-table`, `role="table"` в `frontend/src/app/features/**`):
**31 таблица в 27 файлах.** Серверная пагинация (`mat-paginator`, `page`/`perPage` в API, итог из `meta.total`) — только
у 4: `/people`, `/admin/audit`, `/admin/directory`, `/admin/users`. Остальные получают все строки сразу — сортировка и
фильтры на фронте. Серверной сортировки до этой задачи не было нигде, `MatSort` не используется.

Приоритет: **высокий** — списки сущностей, где сортировка нужна больше всего; **средний** — короткие списки;

Заметки для следующих задач:
- В таблицах без `thead` (16–18, 24, 28 и цикл оценивания 13) сначала нужна строка заголовков.
- Таблицы без пагинации грузят все строки; если список растёт (активы, обращения, заявки), при переводе стоит решить,
  не перейти ли на серверную пагинацию — тогда сортировка тоже уходит на сервер.
- `/people` показывает пагинатор и в виде «карточки»: состояние сортировки и фильтров общее для обоих видов (оно в адресе).
