# API: документация и примеры запросов

## Простыми словами
У SinHRM есть HTTP API — через него работает веб-интерфейс, а разработчик может вызывать его напрямую.
Описание API **не пишется руками**: оно собирается автоматически из кода (маршрутов, правил проверки полей
и ответов) и поэтому не отстаёт от кода.

- **Где смотреть:** `https://<адрес>/api/docs` — интерактивная страница со всеми запросами, сгруппированными
  по модулям (People, Recruiting, TimeOff …). Сырой файл спецификации — `/api/docs.json`.
- **Кто видит:** только **суперадмин**, вошедший в систему. Гость получит 401, остальные роли — 403.
  Публично (без входа) документация не открывается ни на одном окружении.
- **Готовые примеры запросов** — в папке [`rest/`](../../rest): по файлу на модуль, `rest/<модуль>/<модуль>.http`.
  Их можно запускать прямо из PhpStorm/IntelliJ или VS Code (расширение REST Client).
- В CI спецификация собирается на каждом PR; если сборка ломается — CI красный. Готовый `openapi.json`
  лежит в артефакте `openapi` у прогона CI (30 дней).

## Как вызвать API вручную (сессия + XSRF)
API работает на сессионной cookie Laravel Sanctum (SPA-режим), вход — только через Google. Поэтому токен
«из воздуха» получить нельзя — берём его из браузера:

1. Войдите в SinHRM в браузере обычным способом.
2. DevTools → Application → Cookies → адрес API. Скопируйте:
   - `sinhrm-session` — это `session`;
   - `XSRF-TOKEN` — это `xsrf` (значение **url-декодируйте**: `%3D` → `=`).
3. Создайте рядом с `rest/http-client.env.json` файл `rest/http-client.private.env.json`
   (он в `.gitignore`, в репозиторий не попадёт):
   ```json
   { "local": { "session": "<значение cookie>", "xsrf": "<декодированный XSRF-TOKEN>" } }
   ```
4. Откройте нужный `.http`, выберите окружение `local` и выполните запрос.

Чистая сессия без браузера: `GET {{host}}/sanctum/csrf-cookie` выдаёт свежую cookie `XSRF-TOKEN`, но войти
всё равно нужно через Google.

## Технические заметки
- **Генератор:** [dedoc/scramble](https://github.com/dedoc/scramble) (MIT). Он читает FormRequest-правила,
  API Resources и типы возвращаемых значений — аннотации `@OA` писать не нужно. Хотите уточнить описание
  операции — PHPDoc над методом контроллера (первая строка становится summary).
- **Настройки:** `backend/config/scramble.php` (middleware доступа, заголовок); регистрация маршрутов и
  группировка по модулям — `backend/app/Providers/AppServiceProvider.php`. Тег операции = имя модуля из
  namespace контроллера `App\Modules\<Модуль>\…`. Маршруты самой документации в спецификацию не попадают.
- **Доступ:** middleware `web`, `auth:sanctum`, `EnsureUserIsActive`, `can:manage-integrations`
  (тот же гейт, что у админки интеграций = суперадмин). Покрыто тестом `backend/tests/Feature/ApiDocsTest.php`.
- **Локально:**
  ```bash
  cd backend
  php -d memory_limit=1G artisan scramble:export --path=openapi.json   # файл спецификации
  php -d memory_limit=1G artisan scramble:analyze                      # предупреждения генератора
  ```
  Генератору нужна БД с применёнными миграциями (он читает колонки моделей). Лимит памяти по умолчанию
  (128 МБ) мал — отсюда `-d memory_limit=1G`.
- **Известное предупреждение:** `UpdateIntegrationRequest::rules()` зависит от параметра маршрута
  `{integration}`, поэтому тело `PUT /api/integrations/{integration}` в спецификации без полей.
- **Почему файл не закоммичен:** точный вывод зависит от БД (Postgres в CI, SQLite локально) и `APP_URL`,
  проверка «дрейфа» давала бы ложные падения. Источник правды — код; артефакт CI — снимок для потребителей.
- **Расширение (Clipper)** ходит в `/api/clipper/*` по Bearer-токену, а не по сессии — см. [recruiting](../modules/recruiting.md).
- **`.http`-файлы** — стартовые примеры основных запросов модуля (сгенерированы по спецификации и
  вычитаны): данные вымышленные, `@id = 1` в шапке — заглушки, замените реальными id из list-запроса.
  Полный список операций — в `/api/docs`.
