# Реестр поручений для передачи проекта

## Простыми словами
Таблица «поручение владельца → задача в Jira → PR → тесты → выкладка → следующий шаг и владелец». По ней любой
разработчик, имея код и Jira, видит, что действительно работает у людей, что только влито в код, что лежит черновиком
и что ждёт внешнего. Сводный отчёт о выполненных работах по эпикам — задача Jira [HRM-83](https://itstep.atlassian.net/browse/HRM-83). Состояние на 2026-10-09: `main` 11d2d0b2.

## 1. Как читать статусы

Статусы раздельные, смешивать нельзя:

| Статус | Что значит | Можно закрывать тикет |
|---|---|---|
| **Выполнено и deployed** | код влит и работает на боевом хостинге | да, после приёмки владельцем |
| **Только merged** | код в `main`, но нигде не выложен | нет, закрывать после выкладки и приёмки |
| **Draft** | PR открыт, в `main` нет | нет |
| **Blocked** | ждёт внешнего (доступ, договор, DevOps) | нет |

**Что такое stage и что значит «deployed».** Vercel был инструментом и больше не нужен: среда разработки — локальная, на
MySQL 8.4, исходники в git, задачи в Jira. **Stage — крайняя точка готовности задачи**: это локальный запуск на MySQL 8.4
(инструкция и проверки — PR #216; после merge #215 — `docs/guides/deploy-mysql.md`) или stage IT STEP, когда DevOps его развернут (HRM-2). Задача
готова, когда код в git, CI зелёный и работоспособность проверена на stage. Прежний боевой сервис на Vercel работает на
замороженном релизе (ветка замороженного релиза, имя — в [mysql-cutover.md](mysql-cutover.md#замороженный-боевой-релиз-до-cutover),
коммит 8875ac4e, 2026-10-08); автовыкладка `main` на Vercel выключена с PR #176 (`VERCEL_DEPLOY_ENABLED`, [deploy.md](deploy.md)).
Столбец «Только merged» ниже означает «ещё не проверено на stage», а не «не выложено на Vercel».

Проверка по коммиту, воспроизводимая:

```bash
git fetch origin
# 0 — коммит PR в боевом релизе (deployed); 1 — только в main (merged only)
git merge-base --is-ancestor <sha слияния PR> origin/<ветка замороженного релиза>; echo $?
```

На 2026-10-09 из 199 влитых PR (на момент снимка) в замороженном релизе на Vercel 166 (до #175 включительно), только в `main` 33 (список в разделе 5); на stage проверялось только то, что отмечено в тикетах.

**Правило закрытия.** Тикет по одному merge без подтверждения выкладки и приёмки не закрываем. Статус «Готово» у задач
HRM-35…HRM-75 означает «код влит» (и для PR до #175 — «выложен на Vercel»); формальной приёмки вживую нет, она ждёт
stage (HRM-39) и тикетов HRM-14…HRM-20.

## 3a. Решения по умолчанию, ждущие подтверждения владельца

Эти решения приняты и работают, владелец (Дмитрий Запорожец) может их изменить; открытыми вопросами они не являются.

* **Единственный суперадмин решает свои заявки** (режим break-glass), запись `self_decision` попадает в аудит; HR-менеджер и админ при наличии второго админа — нет. Риск R9 в [отчёте аудита](../security/audit-2026-10.md).
* **Табель:** согласование определяется ролями, код не менялся (решение владельца 2026-10-07).
* **Дамп для DevOps** выгружается без секретов интеграций, сессий и токенов; интеграции подключаются заново.
* **Перенос боевых данных не нужен:** данные тестовые, DevOps стартуют с переданного дампа.

## 4. Что делает владелец вне кода

* Выключить Vercel и прежнюю боевую базу после запуска stage; пароль прежней базы менять нужно только если её оставляют работающей (HRM-82).
* Удалить ветку замороженного релиза после выключения Vercel (команда `git push origin --delete <имя ветки>`, имя — в [mysql-cutover.md](mysql-cutover.md)).
* Подтвердить или изменить решения из раздела 3.

## 6. Как вести реестр

1. Новая задача или правка — сначала искать тикет в Jira (JQL `project = HRM AND summary ~ "слово"`), дубль не заводить; если нет — новый тикет под эпиком, компонент `hrm`, спринт активный.
2. В описании PR — ключ Jira; в тикете — номера PR и статус из раздела 1.
3. После merge в тикет пишется «merged, не deployed» и что осталось; «Готово» — только после выкладки и приёмки.
4. При смене статуса обновить строку таблицы выше в том же PR и сводный отчёт HRM-83 (раздел «Сделано по эпикам»).
5. Спринтовый отчёт строит сама Jira: доска HRM Scrum → «Отчёты» → «Отчёт по спринту»; список выполненного — JQL `project = HRM AND statusCategory = Done ORDER BY updated DESC`.
