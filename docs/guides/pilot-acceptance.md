# Протокол приёмки ограниченного пилота

## Статус и выбранная граница

Live-приёмка по этому протоколу **не выполнена**. Нужны аккаунт владельца, утверждённое окружение и выбранный scope.
Предложение для первого пилота — одна организация и recruiting journey; это **OWNER PENDING**, а не разрешение
изменить production. Состав модулей, роли, филиалы, данные, даты и критерии завершения владелец утверждает отдельно.

| Решение перед запуском | Что записать в закрытом протоколе |
|---|---|
| Окружение и версия | Утверждённое окружение, реально развёрнутый Web/API SHA, дата проверки |
| Scope | Организация, филиалы, разрешённые сценарии, выбранные небазовые модули и необходимые зависимости |
| Аккаунты | Имена ролей и разрешённые филиалы; доступ оператора к owner-approved аккаунтам |
| Исключения | Все небазовые модули вне scope явно выключены; причины оставленных зависимостей |
| Приёмка | Ответственный, критерии PASS/FAIL, допустимые ограничения и действия при провале |

Не запрашивать пароль, session cookies, CSRF/Google tokens или ключи в чате/публичном issue. Войти обычным
способом в разрешённом браузере; секреты интеграций вводить только через соответствующее защищённое хранилище.
Google OAuth в текущей конфигурации работает на production-домене; preview сам по себе не доказывает реальный вход
([development](development.md)). Не обходить авторизацию fixture или подменой `/api/auth/me`.

## Настройка модулей и независимых провайдеров

1. Владелец входит как **superadmin** и открывает `/admin/modules` / `GET /api/modules`.
   Снять текущую матрицу enabled/roles до изменений в закрытый журнал без секретов.
   Только superadmin меняет её; admin не получает это право по умолчанию.
2. По утверждённому scope оставить нужные модули и их зависимости. Остальные **небазовые** явно выключить:
   default/missing setting означает enabled, отсутствие галочек в плане не является отключением.
   Например, Workflows вне scope требует собственного disabled setting, даже если Scripts уже выключен.
3. Базовые `auth`, `core`, `directory`, `integrations`, `observability`, `overview`, `users` выключить/ограничить
   этим механизмом нельзя. Зафиксировать это как границу пилота, а доступ к их операциям проверить штатными gates.
4. Для включённых небазовых модулей явно записать allowed roles. Superadmin сохраняется в ролях автоматически
   и видит включённые модули; disabled закрывает модуль также для него. Матрица модулей не расширяет business
   policies, contextual hiring roles или branch scope.
5. **AI и провайдеры проверить отдельно.** Скрытый/выключенный модуль UI не является доказательством отключения
   транзитивных AI/email/calendar/channel calls из других модулей. Проверить штатный AI enabled policy,
   auto-screening settings и конфигурации конкретных интеграций/автозапусков. Если внешние вызовы исключены,
   отключить их соответствующими контролами и подтвердить отсутствие отправки при реальном сценарии.
   Не считать `modules.ai=false` универсальным запретом всех провайдеров. Ключи, prompts и содержимое данных не логировать.

## Реальная проверка через браузер и HTTP API

Использовать действующую сессию и реальные backend ответы, без `installMock`, перехвата маршрутов или offline fixture.
Создавать только разрешённые владельцем тестовые записи в пилотном окружении; заранее согласовать очистку.

| Шаг | Реальное доказательство |
|---|---|
| Вход / выход | Войти обычным login, проверить `GET /api/auth/me`, роли и modules; выйти, закрытый endpoint возвращает 401 |
| Module boundary | Меню и прямая ссылка исключённого модуля закрыты; API возвращает module_disabled/module_forbidden согласно матрице |
| Настройка | Admin не меняет module settings (403); superadmin не выключает core (422 module_core) |
| Заявка / вакансия | Пройти существующий утверждённый approval route, получить связанную vacancy; если HiringRequests не в scope, создать vacancy разрешённым способом |
| Кандидат | Создать кандидата и заявку на выбранную vacancy, проверить карточку и источник; повтор не добавляет дубликат |
| Решение | Реально переместить на следующий stage и отметить hire/reject; reject без причины отклоняется, состояние сохраняется |
| Отчёт | Период/филиал соответствует созданным данным; точные counts и строки согласованы с карточками, чужой филиал отсутствует |
| Негативные права | Viewer и recruiter другого филиала не меняют заявку; чужая карточка/отчёт не раскрывают запрещённые данные |
| Изолированная роль | Повторить проверки из отдельных сессий owner-approved пользователей; admin-wide отчёт не заменяет recruiter scoped proof |

Для Workflows, если он включён в scope: только в согласованном безопасном окружении создать due workflow без
внешних действий, выключить модуль, дождаться разрешённого tick и проверить `module_disabled`, неизменность
шагов и отсутствие workflow task. После включения следующий tick создаёт одну задачу, дальнейший tick её не дублирует;
человеческое закрытие задачи проверяется отдельно. Такая последовательность выполнена только как Feature test (`ModuleAccessTest`)
в синтетической БД. Не вызывать production ops и не менять production настройки ради доказательства без разрешённого плана.

## Телефон, клавиатура и профиль

На реальном backend повторить минимум login, список/фильтры кандидатов, карточку, доступное решение и отчёт
на desktop и **375px**. Проверить, что кнопки, поля/ошибки и таблицы доступны без горизонтального ухода важных действий;
меню закрывается/открывается, диалоги прокручиваются и фокус возвращается.

Клавиатурой: Tab/Shift+Tab проходят основные действия в логичном порядке, Enter/Space активируют их,
Escape закрывает диалог, виден focus; после ошибки можно исправить поле и повторить. Для board использовать
доступное «Перемістити в…», не ограничивать приёмку мышиным drag.

При выбранном People/profile scope пройти вкладки `/people/{id}` и профиль `/me` из реального аккаунта сотрудника
с корректной привязкой. Проверить mobile и keyboard отдельно: существующий parity inventory помечает вкладки
профиля как desktop-only, поэтому его mobile skip не является PASS для этих вкладок.

## Что покрывает автоматизация сейчас

- `ModuleAccessTest` проверяет defaults, module/role denial, superadmin-only settings, core restriction и ops skip.
  Новый focused test создаёт due workflow через HTTP и проверяет неизменность run/step/workflow tasks при disabled,
  реальное выполнение после re-enable и последовательный повтор tick, с неизменным unrelated followups result.
- HiringRequests/Recruiting/Reports Feature tests проверяют DB/HTTP contracts и scope на синтетических данных.
  Сквозная API-приёмка не заменяет Google login, UI, live providers или concurrent exactly-once guarantees.
- `frontend/e2e/harness.ts` обслуживает API из fixtures и формирует mock mutation responses; внешняя сеть блокируется.
  Такие E2E подтверждают UI-инвентарь/взаимодействие, но не реальное изменение backend.
- `frontend/e2e/flows.pw.ts` имеет desktop-light и отдельные mobile-light flows; это разные subsets,
  а не автоматическое повторение каждого desktop сценария на телефоне.
- `frontend/e2e/pages.mjs` использует `tab(...only: desktop)` для вкладок профиля;
  `parity.pw.ts` пропускает несовпадающий viewport. Dark/light/parity PASS не закрывает явно пропущенный сценарий.

Точные выполненные CI jobs/head и skip counts записать по фактическому run; discovery тестов не означает их успешный запуск.
Без owner account live-пункты остаются **NOT EXECUTED**, без утверждённого scope — **OWNER PENDING**.

## Решение и остановка

Для каждого пункта сохранить PASS/FAIL/NOT EXECUTED, роль, viewport, публичный код ответа и минимальное
обезличенное доказательство; не сохранять credentials, персональные поля, prompts или secret values.
Нарушение scope/прав, потеря операции на mobile или необъяснённое расхождение отчёта блокирует соответствующий сценарий.
Восстановить согласованную module matrix по плану владельца, остановить новые действия и передать точный воспроизводимый
дефект. Расширение scope, новые роли, отправка провайдерам и production rollout требуют отдельного решения владельца.
