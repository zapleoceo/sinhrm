# Развёртывание на MySQL 8.4

Решение — [ADR 0010](../adr/0010-mysql.md). Требования приложения к среде (PHP, сборка, переменные, маршрутизация) —
[itstep-app-handoff.md](itstep-app-handoff.md); здесь — только база данных и то, что вокруг неё.

## Подготовка БД

- Сервер — **MySQL 8.4 LTS**, движок InnoDB.
- База создаётся пустой, с кодировкой и collation приложения:
  ```sql
  CREATE DATABASE sinhrm CHARACTER SET utf8mb4 COLLATE utf8mb4_0900_ai_ci;
  ```
- `sql_mode` (строгий, `ONLY_FULL_GROUP_BY`), часовой пояс сессии (`+00:00`), кодировку и collation соединения задаёт само
  приложение (`backend/config/database.php`, соединение `mysql`) — серверные настройки по умолчанию менять не нужно.
- `max_allowed_packet` не ниже 16 МиБ на сервере и у клиентов (`mysql`, `mysqldump`): документы до 2 МиБ лежат в БД
  base64 (`documents_files.content`, ≈ 2,7 МиБ на строку). Значения MySQL 8.4 по умолчанию подходят.
- Переменные окружения приложения: `DB_CONNECTION=mysql` (по умолчанию), `DB_URL=mysql://<user>:<password>@<host>:3306/<db>`
  (или `DB_HOST`/`DB_PORT`/`DB_DATABASE`/`DB_USERNAME`/`DB_PASSWORD`). Строка подключения — только из секрет-хранилища в
  окружение процесса, не в командной строке, не в истории shell и не в Git.

## Учётные записи

| Учётная запись | Права на базу приложения | Кто использует |
|---|---|---|
| миграции | `ALL PRIVILEGES` на `sinhrm.*` (DDL: создание и изменение таблиц и индексов) | шаг релиза `php artisan migrate --force` |
| приложение | `SELECT, INSERT, UPDATE, DELETE` на `sinhrm.*` | PHP-процесс приложения |
| резервные копии | `SELECT, SHOW VIEW, TRIGGER, LOCK TABLES, EVENT` на `sinhrm.*` (+ `PROCESS` при необходимости) | `mysqldump` ([backup-restore.md](backup-restore.md)) |

Если миграции запускаются через `POST /api/ops/migrate` (заголовок `X-Ops-Secret`), а не из консоли, приложению нужны права
учётной записи миграций. Для IT STEP рекомендуется консольный `migrate` отдельной учётной записью.

## Миграции

1. Первый запуск — на **пустой** базе: DDL в MySQL не транзакционный, упавшая миграция оставляет частично созданные
   таблицы; тогда базу пересоздают и запускают заново.
2. Каждый релиз: `cd backend && php artisan migrate --force` в окружении релиза **до** переключения трафика.
   `php artisan migrate:status` — проверка, что ожидающих миграций нет.
3. Режим `?fresh=1` эндпоинта `/api/ops/migrate` (пересоздание БД с синтетикой) в production запрещён кодом.
4. Среди миграций есть миграция данных `Recruiting/Database/Migrations/2026_10_28_100001_mark_sent_offer_touchpoints`:
   помечает письма уже отправленных офферов (`touchpoints.meta.kind = offer`), чтобы таймлайн скрывал зарплату. Только
   `UPDATE` поля `meta` порциями по 200, повторный запуск ничего не меняет; `down()` пустой намеренно.

## Резервные копии

`mysqldump` с `--single-transaction` и изолированное восстановление — [backup-restore.md](backup-restore.md). Вместе с
дампом хранится постоянный `APP_KEY` (им зашифрованы `integration_secrets` и другие зашифрованные поля): дамп без ключа не
восстанавливает интеграции.

## TLS

Если сервер требует TLS, задать `MYSQL_ATTR_SSL_CA=<путь к CA-сертификату>`: приложение тогда включает и проверку
сертификата сервера (`MYSQL_ATTR_SSL_VERIFY_SERVER_CERT`). Без переменной соединение идёт без проверки сертификата —
допустимо только внутри доверенной сети.

## Плановые задания (cron)

Отдельный `queue:work` не нужен: фоновые задачи (`Core\Contracts\ScheduledJob`) запускаются вызовом
`POST https://<внешний-origin>/api/ops/jobs/run` с заголовком `X-Ops-Secret` каждые 30 минут. Сейчас это делает
`.github/workflows/cron.yml`; на инфраструктуре IT STEP — планировщик DevOps с тем же интервалом, секрет — в защищённом
окружении планировщика, в журнал — только HTTP-статус, поле `ok` и счётчики.

## Проверка после развёртывания

- `GET /api/health` → `{"ok":true,...}` (проверяет подключение к БД; при ошибке — HTTP 503).
- `php artisan migrate:status` — все миграции `Ran`.
- Вход через Google и открытие любой страницы SPA — сессии и кэш хранятся в MySQL (таблицы `sessions`, `cache`).
