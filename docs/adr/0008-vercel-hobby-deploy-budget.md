# ADR 0008 — Бюджет деплоев Vercel Hobby: preview только по метке

**Статус:** принято (2026-09-26). Подробности — [guides/deploy.md](../guides/deploy.md).

**Контекст.** Vercel Hobby — 100 выкладок в сутки. Каждый зелёный push в PR давал две (API и сайт); 2026-09-26
лимит был исчерпан.

**Решение.** `deploy.yml` запускается только после зелёного CI. `main` → production всегда; Pull Request →
preview **только с меткой `preview`** (шаг `gate` читает метки PR). Preview-сайт ходит в preview-API того же PR
(перезапись `vercel.json` в CI), на preview только синтетические данные (`/api/ops/migrate?fresh=1`). Деплои PR
отменяются новыми push, деплой `main` — никогда (миграции).

Дополнительно (2026-09-26): job `gate` также решает, какой из двух Vercel-проектов реально нужно деплоить —
`api` (изменения в `backend/**` или в самом `deploy.yml`) и/или `web` (`frontend/**`, `docs/**` или `deploy.yml`).
Для прода база сравнения — sha последнего успешного продовского деплоя; для превью — merge-base PR и `main`.
На превью изменение `web` форсирует `api=true`, чтобы превью-сайт никогда не смотрел на прод-API (иначе публичный
превью-логин открывал бы доступ к реальным данным); на проде `api`/`web` независимы. Логика — в
`.github/scripts/deploy-gate.js`, с юнит-тестами в `deploy-gate.test.js`. Раньше каждый прогон выкладывал оба
проекта независимо от того, что изменилось, — это и было основным источником трат бюджета.

**Последствия.** Лимит тратится на прод и на осознанно запрошенные превью, а также только на те проекты
(API/Web), которые реально изменились. PR без метки проверяется CI и локально; метку ставят, когда нужен живой
стенд.

**Альтернативы.** Preview на каждый push (упирается в лимит), платный план Vercel (бюджет $0), отказ от превью
(теряется ручная проверка интерфейса).
